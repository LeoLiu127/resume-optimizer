# 分析结果持久化与自动恢复设计

## 背景与根因

当前九步智能优化结果只保存在 `useResumeAnalysis` 的 React 内存状态中。
服务端已经存在 `analyses` 表和基础保存、读取 API，但前端从未调用这些
API；当前数据库中也没有任何分析记录。因此，只要应用重新挂载、页面刷新、
重新登录或重新加载简历，JD 解析、简历诊断、匹配分析、优化结果等全部丢失。

单纯点击左侧步骤导航不应清空 React 状态。产品需要进一步保证：查看“输入
材料”不是上下文切换，不能让已经成功生成且输入仍一致的结果失效。

## 目标

1. 一次成功的智能优化应保存完整九步结果。
2. 同一账号、同一份有效输入自动恢复最近一次成功结果。
3. 切换步骤、刷新页面、重启服务、重新登录和重新加载同一简历后结果仍可用。
4. JD、简历正文或影响分析的求职条件发生实质变化后，旧结果不得冒充当前结果。
5. 输入发生变化时只让旧结果失效，不删除数据库历史。
6. 保存或恢复失败不能破坏刚生成的内存结果，也不能恢复其他用户或其他上下文的数据。

## 不在本次范围

- 不增加分析历史列表、版本对比、重命名或删除界面。
- 不改变九步流程、页面视觉风格、分析结果 Schema 或 MiniMax 供应商。
- 不持久化仅用于展示的弹窗、复制成功提示和加载动画。
- 不改变现有追问长期记忆规则。
- 不自动回填无法可靠计算上下文指纹的旧分析记录。

## 方案比较

### 方案 A：服务端按输入指纹保存并自动恢复（采用）

为有效分析输入生成稳定指纹。成功分析后保存结果；恢复时只查询当前用户下
指纹完全一致的最新结果。

优点：

- 跨刷新、登录和服务重启可靠保存。
- 不依赖简历记录 ID，自动保存为简历分配新 ID 后仍能匹配相同内容。
- 服务端用户隔离与输入指纹共同防止串数据。
- 不需要新增历史管理界面。

### 方案 B：仅保存到 `localStorage`

实现较快，但不能跨设备，清理浏览器数据后丢失，也难以复用现有服务端
`analyses` 表。账号隔离和容量限制也更脆弱。

### 方案 C：按简历 ID 恢复最后一次分析

查询简单，但同一简历修改 JD 或正文后容易恢复过期结果；未保存草稿以及自动
保存刚分配 ID 的场景也不稳定。

## 上下文身份

持久化匹配使用“内容身份”，不使用简历 ID 或岗位 ID。参与指纹的字段为：

- 目标岗位；
- 目标行业；
- 目标公司类型；
- 当前求职阶段；
- 希望突出能力；
- 完整 JD；
- 完整简历正文；
- 补充信息。

生成指纹前只做稳定标准化：

- `null`、`undefined` 视为空字符串；
- Windows 换行统一为 `\n`；
- 去除字段首尾空白；
- 不折叠正文内部空格或换行，避免把实质编辑误判为相同。

前端生成稳定的上下文序列化字符串。服务端对该字符串计算 SHA-256，并只存储
哈希值，不在分析表中额外复制简历全文。

同一账号下，指纹相同表示可以复用。两个不同简历记录只要参与分析的内容完全
相同，也允许复用同一结果；这符合“JD 和简历内容不变”的产品规则。

## 数据库设计

对现有 `analyses` 表做向后兼容迁移：

- 新增可空字段 `context_hash TEXT`；
- 新增字段 `engine TEXT NOT NULL DEFAULT ''`；
- 新增索引 `(user_id, context_hash, created_at DESC)`。

旧记录的 `context_hash` 保持为空，不参与自动恢复。迁移不删除或改写任何现有
记录。

同一上下文再次执行智能优化时继续插入新记录，不覆盖旧结果。恢复始终选择
`created_at` 最新的一条；如果时间相同，以 `rowid` 或 ID 作为稳定次级排序。

## API 设计

### 保存结果

继续使用 `POST /api/analyses`，扩展请求体：

```json
{
  "resumeId": "可选",
  "contextKey": "稳定序列化字符串",
  "target": {},
  "jd": "完整 JD",
  "extras": "补充信息",
  "result": {},
  "variant": "balanced",
  "engine": "minimax-m3"
}
```

`contextKey` 和 `result` 必填。服务端校验可选的 `resumeId` 属于当前用户，
计算 `context_hash` 后插入记录。

### 恢复结果

新增 `POST /api/analyses/restore`：

```json
{
  "contextKey": "稳定序列化字符串"
}
```

服务端只在当前登录用户的数据中查询，返回：

```json
{
  "analysis": {
    "id": "记录 ID",
    "result": {},
    "variant": "balanced",
    "engine": "minimax-m3",
    "createdAt": "时间"
  }
}
```

无匹配记录时返回 `{ "analysis": null }`，不是错误。

采用 POST 而非查询字符串，是为了避免完整上下文序列化结果超过 URL 长度限制。

## 前端状态流

### 成功生成

1. 保持现有中英双语预处理和 MiniMax 分析顺序。
2. 模型成功返回后立即显示内存结果并记录 `analyzedInput`。
3. 后台调用保存 API。
4. 保存失败时保留当前结果，显示非阻塞的“结果暂未保存”提示；不要求重新调用模型。

### 自动恢复

以下场景在输入和登录用户恢复完成后尝试恢复：

- 页面首次加载或刷新；
- 重新登录进入工作区；
- 选择或重新加载一份简历；
- 应用岗位或恢复本地草稿后形成稳定输入。

恢复过程根据当前输入生成上下文指纹。只有响应仍对应当前用户和当前指纹时才
应用结果，避免迟到请求覆盖后来选择的简历。命中后：

- 写入 `useResumeAnalysis` 的 `data` 和 `engine`；
- 将当前输入复制到 `analyzedInput`；
- 设置 `analysisStarted = true`；
- 恢复保存的优化风格；
- 保持当前所在步骤，不强制跳转。

没有命中时保持“待生成”或“输入已变化”的状态。

### 导航与失效

- 左侧步骤导航只修改 `activeStep`，绝不清空结果。
- 仅返回“输入材料”、查看字段、打开管理面板或岗位面板，不使结果失效。
- 参与指纹的输入发生变化后，`analysisIsCurrent` 立即变为 `false`，后续步骤
  禁止使用旧结果。
- 如果用户把输入完整恢复为原值，内存中仍有结果时立即重新可用；页面重载后
  也可从服务端恢复。
- 明确执行“清空表单”“使用示例数据”“切换到内容不同的简历/岗位”时，沿用
  现有临时状态清理规则，但不删除服务端历史。

## 并发与错误处理

- 每次恢复分配递增请求序号，并记录请求对应的用户 ID 与上下文指纹。
- 响应返回时三者任一不匹配就丢弃响应。
- 分析期间不发起恢复请求，避免旧结果覆盖正在生成的新结果。
- 保存失败与恢复失败均不清空用户输入。
- 未认证错误继续走现有统一登出协议。
- 数据库返回损坏或空的 `result` 时视为未命中，不写入页面状态。

## 测试策略

### 上下文单元测试

- 换行和字段首尾空白标准化后指纹一致。
- JD、简历正文和任一求职条件变化后指纹不同。
- 简历 ID、岗位 ID 变化但有效内容一致时持久化指纹一致。

### API 测试

- 当前用户能保存并恢复完全匹配的最新结果。
- 不同上下文不匹配。
- 不同用户不能恢复对方结果。
- 同一上下文多次保存时恢复最新记录。
- 无匹配时返回 `analysis: null`。
- 旧记录和迁移前数据不被删除。

### 前端状态测试

- 步骤导航不会触发失效。
- 恢复命中后设置结果、引擎、输入快照和风格。
- 输入变化后旧结果不可用。
- 迟到恢复响应不能覆盖新的用户或输入上下文。
- 保存失败时已生成结果继续可用。

### 全量验证

- 后端全部 Node 测试通过。
- 前端生产构建通过。
- 前后端健康检查通过。
- 手工验证：生成一次结果后依次查看 JD 解析、简历诊断、返回输入材料、再次
  进入后续步骤、刷新页面，均不再次调用模型且结果保持一致。

## 验收标准

- 输入不变时，用户无需重复点击“开始智能优化”。
- 返回输入材料再进入 JD 解析或简历诊断，原结果仍存在。
- 刷新、重新登录和重启服务后，同一输入自动恢复完整结果。
- 输入实际变化后，页面明确要求重新生成，不展示或操作旧结果。
- 不发生跨账号、跨 JD 或跨简历内容的数据污染。
- 保存故障不导致本轮成功分析从当前页面消失。
