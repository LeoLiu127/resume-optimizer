# 简历状态隔离与旧数据清理设计

## 背景

当前项目已经完成真实 MiniMax 分析、双语 JD 和派生字段清理，但仍存在以下数据完整性风险：

- 岗位或 JD 已变化，页面仍保留并允许操作上一轮分析。
- 当前追问使用固定 `q1-q8` 标识，可能把上一岗位的临时回答发给新岗位分析。
- 自动保存请求完成顺序不确定，迟到请求可能重新激活或覆盖错误简历。
- 本地草稿键未按用户隔离，异常退出或 Token 失效时可能恢复其他账号的草稿。
- 登出会删除用户明确要求保留的长期追问记忆。
- 相同招聘 URL 每次解析都会新增岗位，已经形成重复岗位记录。
- 401 只清除凭证，不更新当前页面登录状态。
- 数据库存在旧版本生成的重复岗位和完全等于内置示例的简历记录。

## 目标

1. 上传并保存的真实简历不得被自动删除或覆盖。
2. 长期追问记忆在登出、切换岗位和切换简历后继续保留。
3. 当前追问回答只在同一分析上下文中保留，不得串入其他简历或 JD。
4. 任何会改变简历、岗位或 JD 身份的操作必须使旧分析失效。
5. 自动保存的迟到请求不得改变当前激活简历，也不得覆盖其他简历。
6. 本地草稿按用户隔离，旧版全局草稿只能迁移给当时已登录的明确用户。
7. 相同 URL 的岗位解析采用更新语义，不再重复新增。
8. Token 失效时立即退出工作区并清理当前临时状态。
9. 数据库清理先创建可恢复备份，只删除已确认的重复岗位和内置示例记录。

## 不在本次范围

- 不删除任何上传简历。
- 不删除历史账号。
- 不自动重命名同名账号。
- 不为旧账号自动设置密码。
- 不删除或重建招聘网站 `browser-profile`。
- 不改变九步分析流程、分析结果 Schema、页面视觉风格或模型供应商。
- 不把全部分析结果历史迁移到服务端；分析历史持久化作为独立后续功能。

## 方案选择

### 方案 A：上下文隔离与定向修复（采用）

引入可测试的状态策略和自动保存控制器，在现有前后端结构内完成隔离。岗位创建改为服务端按 URL 更新；长期记忆保留在用户作用域；数据库只做精确清理。

优点：

- 改动范围集中，保持现有产品流程。
- 能直接消除跨 JD、跨简历和跨账号污染。
- 数据清理可恢复、可审计。

### 方案 B：只在页面事件中增加 `reset`

在若干点击处理函数中手动清理状态。

缺点：

- 无法解决异步自动保存竞态。
- 新入口出现后容易漏掉清理。
- 无法解决全局草稿键和 401 状态不同步。

### 方案 C：全部状态迁移到服务端

把草稿、当前回答、长期记忆和分析历史全部写入 SQLite。

缺点：

- 会显著扩大本轮范围。
- 需要新增同步冲突策略和数据迁移协议。
- 不符合“不改变原有设计逻辑”的约束。

## 状态模型

### 长期数据

以下数据跨会话保留：

- 服务端已保存简历。
- 用户长期追问记忆 `answerBank`。
- 已绑定的岗位与岗位状态。

登出只清除当前页面状态、本地草稿指针和临时回答，不删除 `answerBank`。

### 当前分析上下文

分析上下文由以下信息组成：

- 当前简历 ID；未保存草稿使用稳定的本地草稿标识。
- 当前岗位 ID。
- 标准化后的目标岗位、JD 和简历正文。

同一上下文中重新解析时保留当前追问回答。以下操作会切换上下文并清空旧分析、临时回答和临时 bullet：

- 选择另一份简历。
- 新建空草稿。
- 应用另一岗位。
- 成功提取新的 JD。
- 清空表单。
- 使用示例数据。

用户仅修改追问回答后重新解析，不视为上下文切换。

### 分析执行状态

开始新分析时立即隐藏旧分析，显示加载状态。只有模型成功返回后，才记录新的 `analyzedInput`。失败时：

- 分析结果为空。
- `analyzedInput` 为空。
- 页面显示真实错误。
- 不显示“已同步”。

基于旧分析的复制、导出、追问 bullet 和风格重写不得在上下文不匹配时执行。

## 自动保存设计

`useResumes` 为每次计划保存分配递增版本号，并记录当前编辑会话 epoch。

- 新输入只覆盖 `pendingRef`，不会被旧请求的 `finally` 清空。
- 请求返回时只有版本号和 epoch 仍是当前值，才允许设置 `activeId`、更新时间和本地草稿 ID。
- 切换简历、清空表单或使用示例数据时，先结束旧 epoch。
- 需要保留旧草稿时允许等待旧保存完成，但旧请求不得重新激活简历。
- 删除简历时取消针对该简历的待保存任务。

本地键改为：

```text
resume.draft.local.{userId}
resume.draft.activeId.{userId}
```

旧版全局键只在存在已登录用户时迁移一次；未登录时不恢复归属不明的草稿。迁移完成后删除旧键。

## 追问记忆设计

- `answerBank` 继续使用 `resume.answerBank.{userId}`。
- `answers` 和 `bullets` 是当前上下文数据，切换上下文时清理。
- 登出时保留当前用户的 `answerBank`，只清理当前回答和当前 bullet。
- `mergeWithMemory` 继续按问题文本指纹匹配，不能仅按 `q1-q8` 继承临时回答。

本次不删除任何现有长期记忆。

## 岗位去重设计

服务端创建岗位时：

1. URL 非空时，对当前用户按标准化 URL 查找现有岗位。
2. 命中后更新岗位内容和 `updated_at`，返回现有 ID，并标记 `created: false`。
3. URL 为空时保持现有新增逻辑，避免错误合并手工创建的同名岗位。
4. 不使用标题作为唯一键，因为不同公司可以存在同名岗位。

并发请求由数据库唯一索引约束：

```sql
CREATE UNIQUE INDEX ... ON positions(user_id, url) WHERE trim(url) <> '';
```

迁移前必须先清理已经存在的 URL 重复记录，否则不创建索引。

## 认证失效设计

API 收到 401 时：

- 清除 Token 和当前用户缓存。
- 派发统一的 `resume:logout` 事件，并携带 `reason: unauthorized`。
- `AuthGate` 监听该事件并立即切换到登录页。
- 工作区清理当前分析、当前临时回答、激活简历指针和用户草稿，但保留长期追问记忆。

手动登出与 401 使用相同的状态清理协议，避免两套逻辑漂移。

## 数据清理范围

执行前复制：

```text
server/data/app.db
```

到带时间戳的：

```text
server/data/backups/app-before-state-cleanup-YYYYMMDD-HHMMSS.db
```

只删除：

- 当前用户下同一 URL 的两条未关联简历的重复岗位，保留已关联简历的最新岗位。
- 两份 `input_json` 与当前 `exampleInput` 所有输入字段完全一致的简历记录。

删除前再次检查：

- 待删岗位 `resumeCount = 0`。
- 待删示例记录与 `exampleInput` 精确匹配。
- 不根据名称、目标岗位或内容长度推断删除。
- 不删除账号、会话、真实简历、长期追问记忆或浏览器 Cookie。

清理后执行外键检查并复核表计数。

## 测试策略

### 单元测试

- 上下文变化会清空旧分析和临时回答。
- 同一上下文重新解析保留当前回答。
- 旧分析与当前输入不匹配时禁止复制、导出和重写。
- 登出保留 `answerBank`，清理当前回答和 bullet。
- 401 派发退出事件。
- 本地草稿键按用户隔离，并正确迁移旧键。
- 迟到自动保存不得设置 `activeId` 或清空更新的 pending payload。

### API 测试

- 同一用户重复提交相同 URL 时返回同一岗位 ID，并更新内容。
- 不同用户可以保存相同 URL。
- URL 为空的同名岗位仍可分别新增。

### 数据验证

- 清理前备份文件存在且大小大于 0。
- 清理后无重复岗位 URL。
- 清理后无精确示例简历。
- 保存简历数量只减少精确示例记录数量。
- `PRAGMA foreign_key_check` 返回空。

### 全量验证

- `npm test`（后端全部测试）。
- `npm run build`（前端生产构建）。
- `/api/health` 返回 `ok: true` 和 `minimaxConfigured: true`。

## 验收标准

- 切换岗位、JD 或简历后无法看到或操作旧分析。
- 同一上下文重新解析不会丢失用户刚填写的追问答案。
- 迟到保存不会改变当前选中的简历。
- 手动登出和 Token 失效都返回登录页，长期追问记忆仍在。
- 相同 URL 再次解析只更新一个岗位。
- 数据库保留所有非示例简历，并有可恢复备份。
- 原有九步流程、双语显示、真实 MiniMax 分析和导出功能保持不变。
